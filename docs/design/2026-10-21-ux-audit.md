# Navigation and recovery UX audit

User request: Create Account must offer a direct sign-in path, and the same attention to navigation and next steps must apply throughout the app.

## Changes

- Welcome owns one auth navigation path. Create Account and Sign In replace that screen when switching, preventing a growing stack of alternating forms. Carry only the email across; passwords stay in their own forms.
- Both forms show explicit account-switch actions with at least 44pt touch targets, readable field prompts, and disabled edits/switches during submission. Create Account explains the UCF email requirement before submitting.
- Password recovery starts with the entered email, provides Back to sign in, and clears stale success feedback when the email changes.
- Email verification offers Use a different email. Verification and resend cannot run simultaneously; a resend cooldown is enforced in the model as well as the UI.
- Onboarding and preferred-sports editing keep Continue/Save visible above the bottom safe area. Onboarding explains disabled Continue, reports selection count, and offers an account-switch escape through the existing sign-out coordinator.
- My Games and attendance-history empty states offer Find a game, which selects Discover and returns its navigation to the feed.
- Filtered empty discovery offers Reset filters. Profile load failures offer retry and pull-to-refresh. Blocked-user loading failures offer retry.
- Create/Edit distinguish loading, empty, and failed venue requests. Failures offer reload; custom location remains available even without the campus venue list. Editing preserves the current venue selection when the list is unavailable.
- Profile uses standard navigation chrome so pushed settings/history retain a clear Back path. Location-search clear and recovery controls have labels and adequate touch targets.

## Sign-in follow-up: simulator Keychain access

The interactive simulator build had been installed after an unsigned build (`CODE_SIGNING_ALLOWED=NO`).
Production logs showed password sign-in returning 200 at 15:32 UTC and public discovery reads succeeding,
but no corresponding own-profile request. Simulator `securityd` logs showed this app's Keychain calls
rejected with `-34018`: missing application-identifier/keychain-access-groups entitlements. Supabase's
session storage could not retain the successful login; subsequent `auth.session` access failed before
Profile could send its request. The app's sign-in UI state alone did not establish a usable SDK session.

`AuthSessionPersistenceTests` reproduces this failure under an unsigned test host, using synthetic
responses and the real simulator Keychain. With signing enabled it verifies session storage, an
authenticated profile request, restoration by another client, and removal on local sign-out. The README
now distinguishes unsigned compilation/static checks from signed interactive builds. Production auth,
account credentials, Keychain storage implementation, and database permissions were not changed.

Signed simulator verification: **218/218 iOS tests passed** (`/tmp/pickup-auth-final-tests.xcresult`).
The signed app was reinstalled and opened at Sign In; diff hygiene passed.

Real-account sign-in after installing the signed simulator build remains a user check; synthetic
responses establish the local storage/authenticated-request behavior without handling the user's password.
